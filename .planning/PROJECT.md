# Stellar Remote — iPad Port

## What This Is

`stellar-ios` is a minimal SwiftUI remote for the Stellar music streamer running
on a Raspberry Pi 5. This project brings that existing iPhone app to iPad as a
first-class citizen: same app, same target, same feature set, but with
iPad-idiomatic navigation, every orientation, and full multitasking support.

All work happens on the branch `feature/ipad-port`, merged to `main` in one
piece when the port is done.

## Core Value

**The iPhone app must not regress.** It is the daily driver for controlling a
bit-perfect audio system. Every iPad change is additive and branches on size
class; if the iPad work ever forces a compromise on the iPhone experience, the
iPhone wins.

## Requirements

### Active

- [ ] App builds and installs on iPad (`TARGETED_DEVICE_FAMILY = "1,2"`)
- [ ] All four orientations supported on iPad
- [ ] Split View and Stage Manager work (`UIRequiresFullScreen` removed)
- [ ] iPad uses `NavigationSplitView` sidebar navigation
- [ ] LCD power and VU toggles work from the sidebar without a "phantom tab"
- [ ] Every existing capability reachable and correct on iPad
- [ ] Layout holds from ~320 pt (Slide Over) to 13" full screen
- [ ] iPhone build byte-for-byte equivalent in behaviour and appearance
- [ ] Full test suite green on iPhone *and* iPad simulators

### Out of Scope

- **New features** — the port adds no capability the iPhone app lacks.
- **Volume control** — deliberately absent. `setVolume`/`toggleMute` stay in
  `SocketService` unused; the audio path is bit-perfect and must stay that way.
- **macOS / Catalyst / visionOS** — iPad only.
- **Backend or frontend changes** — this is a single-repo port. The Socket.IO
  contract is untouched.
- **Fixing the pre-existing scope drift** (ingest, VU toggle) — noted in
  CONCERNS.md, ported as-is, not redesigned here.
- **Annotating stores `@MainActor`** — correct eventual cleanup, but not this
  project's job.

## Context

- Existing codebase is healthy: 205 tests green, clean build with zero warnings
  as of 2026-09-09.
- Full architecture, conventions, testing and risk analysis live in
  `.planning/codebase/` (seven documents).
- Xcode 26.3 is installed, so the iOS 26 SDK and iPadOS 26 behaviours are
  available — and the long-standing App Store submission blocker is cleared
  (separate track, not part of this project).
- Physical iPad arrives 2026-09-10 for on-device testing. Until then, simulator
  only.

## Constraints

- **Tech stack**: Swift / SwiftUI, `@Observable` only. iOS 17.0 deployment
  target — `NavigationSplitView` is iOS 16+, so no floor change is needed.
- **Build**: the `.xcodeproj` is generated by xcodegen from `project.yml`.
  Adding any `.swift` file requires `xcodegen generate --spec project.yml`.
- **Testing**: `swift test` does not work; everything runs on a simulator
  destination selected by UDID (device names are ambiguous across runtimes).
- **Process**: TDD required. Code review required. Commit *and push* at every
  phase boundary.
- **Compatibility**: iPhone behaviour is frozen. Size-class branching, never
  replacement.

## Key Decisions

| Date | Decision | Rationale |
|---|---|---|
| 2026-09-08 | Same Xcode target, not a new project or repo | It is one universal SwiftUI app; a second target would fork 45 files of shared code for no gain. |
| 2026-09-08 | All orientations + Split View / Stage Manager | User choice. `UIRequiresFullScreen` is deprecated on iPadOS 26 and blocks multitasking; keeping it is a growing liability. |
| 2026-09-08 | `NavigationSplitView` sidebar on iPad | User choice, taken knowingly over "same layout, responsive sizing". Costs more work and diverges structurally from the iPhone, but is what iPad users expect. |
| 2026-09-09 | Port *all* shipped capabilities, not literally six | The codebase ships eight user-facing capabilities; ingest and the VU toggle are real and reachable. "Same thing, just on iPad" means all of it. |
| 2026-09-09 | Codebase mapped inline rather than by subagents | `gsd-codebase-mapper` spawns produced no output twice; used the workflow's documented sequential fallback. |
